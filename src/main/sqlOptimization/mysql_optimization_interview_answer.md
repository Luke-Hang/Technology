# 面试题：你们的 MySQL 是怎么优化的？

## 记忆主线

MySQL 优化可以记成一句话：

```text
SQL -> 索引 -> 表和数据 -> 架构
```

面试时建议先说这 4 个角度，再重点展开 SQL 和索引，最后用表数据优化、架构优化作为补充。这样回答完整，而且不会显得很散。

## 面试时可以直接这样说

MySQL 优化我一般从四个方面考虑：SQL 层面、索引层面、表和数据层面、架构层面。

## SQL 层面
1.通过慢查询日志、接口耗时监控定位慢 SQL
2.用 `EXPLAIN` 分析执行计划，
  重点关注看有没有走索引、扫描行数是否过多、有没有全表扫描，以及是否出现 `Using filesort`、`Using temporary`。
3.SQL 写法上会优化 `SELECT *`、复杂 JOIN、大分页、子查询。
  3.1 SELECT * 优化为使用 SELECT <字段列表> 查询
  3.2 子查询优化为 join 操作
    子查询会产生大量的临时表且也没有索引，会消耗过多的 CPU 和 IO 资源，产生大量的慢查询
  3.3 避免使用 JOIN 关联太多表
    同一个 SQL 多关联（join）一个表，就会多分配一个关联缓存，SQL 中关联的表越多，所占用的内存也就越大
    MySQL 最多允许关联 61 个表，但建议不超过 5 个
  3.4对于大数据量的分页查询，避免使用 LIMIT pageSize OFFSET offset 改用基于上一页最后一条记录,做游标分页
    SELECT * FROM orders ORDER BY id LIMIT pageSize OFFSET offset; 
      pageSize   每页显示记录数
      OFFSET=(pageNum - 1) * pageSize   偏移量
    SELECT * FROM orders ORDER BY id LIMIT OFFSET，pageSize; (这种写法和上面那种话写法都可以，种种写法OFFSET，pageSize 之间的逗号不能丢)
    SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 20 == SELECT * FROM orders ORDER BY id LIMIT 20，10
      LIMIT 10 = 每页取 10 条，OFFSET 20 = 偏移（跳过）前 20 条。每页取 10 条，偏移（跳过）前 20 条，也就是查询排序后的第 21～30 条数据
    SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 10,0000===SELECT * FROM orders ORDER BY id LIMIT 10,0000, 10;
      取 10 条，偏移 10,0000 条，那么刚好就取到第10000 页以后的数据，即取第 10,0001-10,0010 条数据
    不加基于游标的分页 SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;(不推荐)
    加基于游标的分页   SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;(推荐)
    推荐公式          SELECT * FROM orders WHERE id > lastPageLastId ORDER BY id LIMIT 10; lastPageLastId(上一页最后一条记录的 id)
    面试题，MySQL当分页分到 10000 页以后的时候，怎么优化？
      MySQL 很典型的 深分页优化面 试题，如果每页 10 条，第 10000 页以后大概就是 OFFSET 10,0000
      MySQL 分页到第 10000 页会出现深分页问题。比如 LIMIT 10,0000, 10，它通常需要先扫描前面的 10,0000 条，再丢掉，只返回最后 10 条
      所以页数越深即 offset 越大，扫描的数据越多，查询越慢。
      优化方案：基于上一页最后一条记录做游标分页 SELECT * FROM orders WHERE id > lastPageLastId ORDER BY id LIMIT 10;
      SELECT * FROM orders WHERE id > 1000000(lastPageLastId) ORDER BY id LIMIT 10;
       这样可以直接利用 id 索引定位，不需要扫描前面大量数据。
      如果必须支持跳到第 10000 页，可以先查主键，再回表
      SELECT o.* FROM orders o
      JOIN (
          SELECT id
          FROM orders
          ORDER BY id
          LIMIT 99990, 10
      ) t ON o.id = t.id;

  3.5 在明显不会有重复值时使用 UNION ALL 而不是 UNION
    UNION 会把两个结果集的所有数据放到临时表中后再进行去重操作
    UNION ALL 不会再对结果集进行去重操作

## 索引层面
1.根据 `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY` 的常用字段建立合适索引。
2.高频查询会设计联合索引，注意最左匹配原则；
3.如果查询字段都能从索引里拿到，也会考虑覆盖索引减少回表。
4.同时索引不是越多越好，会避免重复索引和低价值索引。

## 表和数据层面
比如合理选择字段类型，避免核心表字段过大；
对于历史数据比较多的表，会做冷热数据拆分或历史归档；
对于统计类查询，会考虑汇总表或冗余字段，减少实时聚合大表的成本。

## 架构层面
1.如果单库压力比较大，会考虑 Redis 缓存热点数据、读写分离降低主库压力；
2.如果数据量特别大，再考虑分库分表；
3.如果写入高峰明显，可以用 MQ 做异步化和削峰。

## 一、SQL 层面

SQL 层面主要解决“这条 SQL 写得是否合理”的问题，也是最先考虑的优化方向。

### 1. 定位慢 SQL

常见定位方式：

- 慢查询日志。
- 接口响应时间监控。
- APM 或链路追踪。
- 数据库 CPU、IO、连接数等监控。
- 业务反馈，比如某个列表页、搜索页、统计页越来越慢。

定位时一般优先处理高频核心接口，比如订单列表、商品搜索、支付查询、后台统计等。

### 2. 用 EXPLAIN 看执行计划

定位到 SQL 后，会用 `EXPLAIN` 分析执行计划，重点看：

- `type`：访问类型，尽量避免 `ALL` 全表扫描。
- `possible_keys`：理论上可能使用哪些索引。
- `key`：实际使用了哪个索引。
- `rows`：预估扫描行数，越大越需要关注。
- `Extra`：看有没有 `Using filesort`、`Using temporary`、`Using index`。

如果 `key` 为空、`rows` 很大、`type` 是 `ALL`，通常说明 SQL 或索引需要优化。

### 3. 常见 SQL 优化点

- SELECT * 优化为使用 SELECT <字段列表> 查询
- 子查询优化为 join 操作, 子查询会产生大量的临时表且也没有索引，会消耗过多的 CPU 和 IO 资源，产生大量的慢查询
- 优化复杂 JOIN，避免使用 JOIN 关联太多表
    同一个 SQL 多关联（join）一个表，就会多分配一个关联缓存，SQL 中关联的表越多，所占用的内存也就越大
    MySQL 最多允许关联 61 个表，但建议不超过 5 个
- 大分页避免直接使用很大的 `LIMIT offset, size`。
    改用基于 上一页最后一条记录的 id lastPageLastId(lastPageLastId 是动态传递的，始终是一页最后一条记录的 id)
    SELECT * FROM orders WHERE id > lastPageLastId ORDER BY id LIMIT 10; 
- 能用 JOIN 或合理改写解决的场景，避免低效子查询。
    子查询优化为 join 操作, 子查询会产生大量的临时表且也没有索引，会消耗过多的 CPU 和 IO 资源，产生大量的慢查询
- 避免在索引列上使用函数。
- 避免隐式类型转换。
- 避免 `LIKE '%xxx'` 这种前置通配符。

避免在索引列上使用函数：

```sql
-- 不推荐
WHERE DATE(created_at) = '2025-01-01'

-- 推荐
WHERE created_at >= '2025-01-01'
  AND created_at < '2025-01-02'
```

避免隐式类型转换：

```sql
-- phone 是 varchar 时，不推荐
WHERE phone = 13800138000

-- 推荐
WHERE phone = '13800138000'
```

减少 `SELECT *`：

```sql
-- 不推荐
SELECT * FROM orders WHERE id = ?

-- 推荐
SELECT id, order_no, status, total_amount
FROM orders
WHERE id = ?
```

优化大分页：

```sql
-- 不推荐，offset 很大时会越来越慢
SELECT id, order_no
FROM orders
ORDER BY id
LIMIT 100000, 20;

-- 推荐，基于上一页最后一条 id 翻页
SELECT id, order_no
FROM orders
WHERE id > ?
ORDER BY id
LIMIT 20;
```

## 二、索引层面

索引层面主要解决“数据库能不能高效找到数据”的问题。重点是按查询场景设计索引，而不是看到字段就加索引。

### 1. 常见索引优化点
1.根据 `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY` 的常用字段建立合适索引。
2.高频查询会设计联合索引，注意最左匹配原则；
3.如果查询字段都能从索引里拿到，也会考虑覆盖索引减少回表。
4.避免索引失效。
5.同时索引不是越多越好，避免重复索引和低价值索引。

### 2. 联合索引示例

比如订单列表经常这样查：

```sql
SELECT id, order_no, status, total_amount, created_at
FROM orders
WHERE store_id = ?
  AND status = ?
  AND created_at >= ?
  AND created_at < ?
ORDER BY created_at DESC
LIMIT 20;
```

可以建立联合索引：

```sql
CREATE INDEX idx_orders_store_status_created
ON orders (store_id, status, created_at);
```

这样 `store_id`、`status` 可以做等值过滤，`created_at` 可以做范围查询，也能尽量减少排序成本。

### 3. 覆盖索引和回表

如果查询字段都能从索引里拿到，就可能形成覆盖索引，减少回表。

```sql
CREATE INDEX idx_orders_list
ON orders (store_id, status, created_at, id, order_no, total_amount);
查询字段都能从索引里拿到，形成覆盖索引，减少回表
SELECT store_id, status, created_at, id, order_no, total_amount FROM orders
WHERE store_id = ?
  AND status = ?
  AND created_at >= ?
  AND created_at < ?
ORDER BY created_at DESC
LIMIT 20;

```

这类索引适合高频列表查询，但不能滥用，因为索引字段太多会影响写入性能，也会占更多磁盘空间。

### 4. 索引失效常见情况

- 联合索引不符合最左匹配原则。
- 在索引列上使用函数或表达式。
    WHERE DATE(created_at) = '2025-01-01'
- 字段类型不一致导致隐式转换。
    phone 是 varchar 时
      不推荐 - WHERE phone = 13800138000
      推荐   - WHERE phone = '13800138000'
- `LIKE` 使用前置 `%`。
- `OR` 条件中有一侧没有合适索引。
- 查询返回数据比例太高，优化器认为全表扫描更划算。

### 5. 索引不是越多越好

索引会提升查询效率，但也有成本：

- 插入、更新、删除时要维护索引。
- 索引会占用磁盘空间。
- 索引太多会增加优化器选择成本。
- 重复索引、低价值索引会拖慢写入。

所以一般只给高频查询、过滤条件、排序分组、关联字段建索引，并定期清理长期不用或重复的索引。

## 三、表和数据层面

表和数据层面主要解决“数据结构和数据规模是否合理”的问题。

### 1. 字段类型优化

常见做法：

- 能用较小类型就不用过大的类型。
- 状态、类型字段可以用 `TINYINT`。
- 金额字段使用 `DECIMAL`。
- 时间字段统一规范，方便范围查询。
- 核心列表查询中避免放太多大字段，比如大文本、JSON。

字段越大，单页能存的数据越少，IO 成本也会变高。

### 2. 冷热数据拆分和历史归档

订单、日志、流水这类表会持续增长。如果所有历史数据都放在一张热点表里，索引和查询成本都会越来越高。

常见做法：

- 近期数据留在主表。
- 历史数据归档到历史表。
- 查询历史数据时走单独入口。
- 后台统计尽量不影响核心交易表。

例如：

```text
orders
orders_history
```

这样日常订单列表主要查近期订单，历史订单查询单独处理。

### 3. 汇总表和冗余字段

统计类查询如果每次都扫明细表，数据量大后会很慢。

比如每天统计门店销售额，如果每次都从 `orders` 明细表实时 `GROUP BY`，成本会比较高。可以做一张日维度汇总表：

```text
store_sales_daily
```

通过定时任务或异步消息写入汇总结果，查询报表时直接查汇总表。

适当的冗余字段也可以减少 JOIN，比如订单表里冗余用户名称、商品快照等。但冗余字段要注意一致性边界，不能随便滥用。

### 4. 分区或分表

如果单表数据量特别大，可以考虑：

- 按时间分区。
- 按租户分表。
- 按用户 ID 或订单 ID 分片。
- 按业务类型拆表。

不过分表会增加复杂度，比如路由、跨表查询、分页、事务、扩容都要考虑，所以一般是在单表数据量和访问压力确实上来以后才做。

## 四、架构层面

架构层面主要解决“单库单表或单个数据库节点扛不住”的问题。它通常是数据量、并发量或业务复杂度上来之后才考虑的。

### 1. 缓存

对读多写少、变化不频繁的数据，可以加缓存，比如：

- 商品分类。
- 字典配置。
- 首页推荐。
- 用户基础信息。
- 热点商品信息。

常见做法是 Redis 缓存。需要注意缓存一致性、过期时间、缓存击穿、缓存穿透和缓存雪崩。

### 2. 读写分离

如果读压力明显大于写压力，可以考虑主从复制和读写分离：

- 写请求走主库。
- 查询请求走从库。
- 报表查询、后台查询尽量走从库。

需要注意主从延迟。比如刚下单后马上查询订单详情，最好查主库，避免用户看不到刚写入的数据。

### 3. 分库分表

当单库或单表成为瓶颈时，可以考虑分库分表。

常见拆分方式：

- 按用户 ID 分库分表。
- 按订单 ID 分库分表。
- 按租户拆分。
- 按时间拆分历史数据。

分库分表能解决容量和并发问题，但会带来跨库 JOIN、分布式事务、全局 ID、跨分片分页和聚合统计的问题，所以要结合业务场景谨慎做。

### 4. 异步化和削峰

写入压力大的场景，可以通过 MQ 做异步处理。

比如：

- 下单后异步写操作日志。
- 支付成功后异步发通知。
- 订单完成后异步更新统计表。
- 大批量导入任务异步执行。

这样可以减少核心接口耗时，也能削峰，避免瞬时流量直接打到数据库。

## 项目案例回答

可以这样说：

我们之前有一个订单列表接口，查询条件包括门店、订单状态、下单时间，还要按下单时间倒序分页。数据量上来之后接口变慢，我们先通过慢查询日志定位到这条 SQL，然后用 `EXPLAIN` 看执行计划，发现扫描行数比较多，排序成本也比较高。

SQL 层面，我们把 `SELECT *` 改成只查列表页需要的字段，并且把时间条件统一改成范围查询。

索引层面，我们根据查询条件建立了联合索引：

```sql
CREATE INDEX idx_orders_store_status_created
ON orders (store_id, status, created_at);
```

表和数据层面，我们把历史订单做了归档，日常列表默认只查近期订单，历史订单走单独查询入口。

架构层面，对于一些订单统计数据，我们没有每次实时扫订单明细，而是通过异步任务写入汇总表，后台报表直接查汇总结果。

最后我们对比优化前后的执行计划和接口耗时，扫描行数明显下降，接口响应也从几百毫秒降到了几十毫秒。

## 面试官继续追问时怎么答

### 1. 你们最常用的是哪类优化？

最常用的是 SQL 优化和索引优化，因为这两类成本最低、见效最快。表结构、缓存、读写分离、分库分表属于更高层面的优化，一般要结合数据量和业务压力来做。

### 2. 什么情况下考虑架构优化？

当单条 SQL 已经优化过，索引也比较合理，但整体压力还是很大时，会考虑架构优化。比如读请求太多，就考虑缓存或读写分离；单表数据太大，就考虑归档、分区或分表；写入高峰太明显，就考虑 MQ 异步化。

### 3. 架构优化是不是越早做越好？

不是。架构优化会增加系统复杂度。比如分库分表会带来跨库查询、事务和分页问题；缓存会带来一致性问题；读写分离会带来主从延迟问题。所以一般先做 SQL、索引和表结构优化，确实解决不了再上架构方案。

### 4. 怎么证明优化有效？

主要看四类数据：

- 优化前后的执行计划。
- 扫描行数有没有下降。
- 接口耗时有没有下降。
- 数据库 CPU、IO、连接数等负载有没有改善。

如果只是加了索引，但执行计划没走这个索引，或者接口耗时没改善，就不能算真正优化成功。

### 5. Java 面试最容易追问什么？

Java 后端面试建议重点讲扎实这几块：

- `EXPLAIN` 怎么看。
- 联合索引和最左匹配原则。
- 覆盖索引和回表。
- 索引失效场景。
- 大分页优化。
- 慢 SQL 定位流程。

架构层面作为补充，不要讲得太虚。面试官大概率会继续追问 SQL 和索引细节，比如为什么这个联合索引这样设计、什么情况下不走索引、覆盖索引为什么能减少回表。

## 最推荐的回答顺序

面试时可以按这个顺序说：

1. 先说我们按 SQL、索引、表和数据、架构四层优化。
2. 再说怎么发现问题：慢查询日志、接口监控、`EXPLAIN`。
3. 然后展开每一层做什么。
4. 最后举一个订单列表或报表统计的例子。
5. 结尾强调优化后会验证执行计划和耗时。

核心表达是：小问题不直接上复杂架构，大问题也不能只靠加索引。我们会根据数据量、访问频率和业务场景分层优化。
